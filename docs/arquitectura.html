QASL-TDM · demo.py

Ciclo de vida de un dato de prueba

Los datos se preparan antes, por lote. El test no crea nada: pide una condición de negocio, recibe un registro que ya existía y lo devuelve al terminar.

>python demo.py

Arquitectura

Tres actores, dos ritmos, un pool

La confusión habitual es pensar que crear y consumir datos son el mismo proceso. No lo son: tienen ritmos distintos y por eso viven en módulos separados. La mitad batch corre en un job y nadie la espera. La mitad de runtime responde a cada test en milisegundos.

Estados

Por dónde pasa un registro

Cada fila del pool está siempre en uno de tres estados. Las transiciones no son libres: hay exactamente cinco caminos, y el que más importa es el que no existe — una reserva vencida nunca vuelve directo a disponible.

Recorrido

Los nueve pasos de demo.py

El orden importa: cada paso deja al pool en el estado que necesita el siguiente. La columna de la derecha muestra qué le pasa al registro.

  1. 01

    Estado inicial del pool

    GET /tdm/pool/stats

    El inventario: cuántos registros hay de cada escenario y en qué estado. Es lo que se mira antes de lanzar una regresión, y lo que responde la pregunta “¿tengo datos para correr mañana?” sin preguntarle a nadie.

  2. 02

    SEED — acá nacen los datos

    POST /tdm/pool/seed

    No se le pasan valores, se le pasa el nombre de un escenario. El generador arma registros que cumplen esa condición de negocio, con CUIT, CBU y tarjeta de dígito verificador correcto, y los enmascara antes de guardarlos.

    no existía → AVAILABLE
  3. 03

    RESERVE — un test pide un dato

    POST /tdm/reserve

    Acá no se crea nada. Un SELECT busca el primer registro disponible del escenario y un UPDATE lo marca como tomado. El test no sabe qué cliente le van a dar, y no le importa.

    AVAILABLE → RESERVED
  4. 04

    Concurrencia — otro test pide a la vez

    POST /tdm/reserve · worker-2

    Recibe otro registro, nunca el mismo. Lo garantiza la condición dentro del UPDATE: “marcalo solo si sigue disponible”. El que llega segundo actualiza cero filas y reintenta.

    Sin esto, dos tests en paralelo agarran el mismo cliente, los dos le cambian el saldo y los dos fallan por motivos que nadie entiende.

  5. 05

    La reserva tiene dueño

    POST /tdm/release · 409 Conflict

    worker-2 intenta liberar el dato de worker-1 y el servicio lo rechaza. Protege contra el caso real: un teardown mal escrito que limpia de más.

    RESERVED → RESERVED sin cambios
  6. 06

    RELEASE — el test devuelve el dato

    POST /tdm/release

    Dos salidas posibles. CLEAN: el test no tocó el dato, vuelve directo al pool. DIRTY: el test lo modificó, queda fuera hasta que alguien lo restaure.

    RESERVED → AVAILABLE o DIRTY
  7. 07

    RESET — recuperar el dato sucio

    POST /tdm/reset/{id}

    Regenera la condición de negocio — saldo, estado de cuenta, días de mora — y devuelve el registro al pool.

    No toca la identidad: DNI, CUIT, CBU y tarjeta siguen siendo los mismos. Si cambiaran, un test que guardó el CBU para verificar después dejaría de encontrarlo.

    DIRTY → AVAILABLE
  8. 08

    Auditoría — quién lo tocó y cuándo

    GET /tdm/records/{id}/audit

    La historia completa del registro, con actor y timestamp. No es un documento que alguien escribe: es la traza que deja el sistema, y es lo que exige el punto 9.2.2 de la Comunicación “A” 7724 del BCRA.

  9. 09

    EXPORT — volumen para JMeter

    GET /tdm/pool/export · reserve_for

    Las pruebas de carga funcionan al revés: necesitan volumen precargado en un CSV. Pedir un registro por iteración convertiría al TDM en el cuello de botella de la propia prueba.

    Con reserve_for, cada corrida se lleva registros distintos. Es lo que evita que la segunda pasada reutilice datos ya quemados y dé falsos negativos.

    AVAILABLE → RESERVED en lote, TTL largo

Lo que no pasa en ningún paso

El test nunca escribe un INSERT, nunca elige un cliente de una lista y nunca limpia a mano. Pide una condición, recibe un registro que ya existía y lo devuelve. Todo lo demás lo resuelve el pool.

Ejecución

Dos terminales, en este orden

Ambas paradas en C:\Users\ELYER\Proyectos\QASL-TDM, con el entorno virtual activo. La primera queda ocupada mostrando logs; la segunda es donde se trabaja.

Terminal 1 · la API queda ocupada 
> .\.venv\Scripts\Activate.ps1
> uvicorn app.main:app --reload

# Application startup complete.
# no cerrar, no escribir nada más
Terminal 2 · el recorrido libre 
> .\.venv\Scripts\Activate.ps1
> python cli.py refresh --min 50
> python cli.py stats
> python demo.py

# al terminar, dejar todo como estaba
> python cli.py refresh --min 50
QASL-TDM · el recorrido lo ejecuta demo.py, que se frena en cada paso esperando Enter. Para cortar la API, Ctrl + C en la terminal 1.
